## Engine `src/server/billing/`
- `due.ts`: `findDueSubscriptions(db, on)` → ids of subscriptions with `status = 'active'` and `next_invoice_date <= on` (uses index `subscriptions(status, next_invoice_date)`), ordered by number.
- `build-invoice.ts` (pure): `buildInvoice({ subscription, customer, plan, lines, taxesByProduct, discounts, periodStart, termsDueDays, on })` → `{ header, lines }` ready to insert: period `[periodStart, periodEnd(periodStart, interval, count)]`, `issued_on = on`, `due_date = on + dueDays`, customer snapshot `{ name, email, company, address, gstin }`, line snapshots from `price()` (description = product name, variant label, qty, unit price, tax bps, discount, tax, total), header totals. Unit tests.
- `insert-invoice.ts`: `insertInvoice(tx, built)` → `INSERT … ON CONFLICT (subscription_id, period_start) DO NOTHING RETURNING id`; returns `null` when it already existed. Number `INV-` + 4+ digit `nextval('invoice_number_seq')` (only consumed on success: take nextval inside the INSERT expression). Status `draft` (the only allowed direct status write besides the state machine).
- `run.ts`: `runBilling(db, { on, actor, subscriptionIds? })` → for each due sub, **its own transaction**: lock the sub row `FOR UPDATE`, re-check due, build, insert (skip if conflict), `redeemDiscounts` (if any discount fails its limit, rebuild without it before insert — do redemption check first by pricing, then insert, then redeem; on failure throw to roll back and retry once without the failed discount), advance `next_invoice_date = addInterval(period_start, …)`; if the new date is past `expiry_date`: when `plan.autoClose` → `transitionSubscription(… "closed", system: true)`, else set `next_invoice_date = null`. Catch-up: if a sub is several periods behind, produce one invoice per period (loop while due), capped at 24. Record a `billing_runs` row. Returns `{ runId, created: { invoiceId, number, subscriptionId }[], skipped: { subscriptionId, reason }[] }`.
- `previewBilling(db, on)` → the same build without inserting (for the billing-run deck): `{ subscriptionId, number, customerName, periodStart, periodEnd, lines, subtotal, discountTotal, taxTotal, total, appliedDiscounts }[]` plus totals.
- Tests (DB): run creates N invoices with correct totals/snapshots; **running twice creates nothing new** (idempotency); concurrent `runBilling` ×2 in parallel → still exactly one invoice per period; catch-up of 3 periods; auto-close at expiry; usage-limited discount applied only up to its limit across a run; snapshot unchanged after the product price changes.

## Invoices `src/features/invoices/`
- `service.ts`: `confirmInvoice`, `cancelInvoice`, `sendInvoice` (confirms if draft, emails the customer via `src/server/mail.ts` with a link to `/invoices/:id`, sets `sent_at`, logs activity "sent"), `bulkConfirm(ids)`, `bulkSend(ids)` — all via `transitionInvoice`.
- `queries.ts`: `listInvoices(db, ListParams & { status?, view?: "all" | "draft" | "unpaid" | "overdue" | "paid", customerId?, subscriptionId?, today })` → rows `{ id, number, customerName, subscriptionNumber, issuedOn, dueDate, total, amountPaid, balance, status, displayStatus }` where `displayStatus` adds derived `overdue` / `partially_paid`; `getInvoice(db, id)` → header, snapshot, lines, payments, activity, `availableActions`.
- `actions.ts`: staff + admin. `src/features/billing/actions.ts`: `runBillingAction`, `previewBillingAction` (admin + staff).
